# メール送信の設定（Resend・Supabase Auth）

本部先行の運用開始に向けて、メールを送れるようにするための設定です（2026-11-25 の工程の M1）。
キーなどの秘密の値は、このファイル・GitHub・チャットに書きません。

## 送るメールと経路

| メール | 送る仕組み | 設定する場所 |
| --- | --- | --- |
| 通知メール（問い合わせ・見積依頼・見積の発行など） | アプリから Resend の HTTP API（`lib/mail/send.ts`） | Vercel の環境変数 |
| 会員登録の確認・パスワード再設定 | Supabase Auth から SMTP（Resend の SMTP） | Supabase の Authentication の画面 |

## 既存の送信を守る決まり（2026-11-25）

Resend は、千の風様の既存のアカウント（チーム）を使います。同じチーム・同じドメインで、ほかの送信が動いている前提で、次を守ります。

- DNS（MX・SPF・DKIM・DMARC）は変えない。Resend 用の記録はすでにある（`resend._domainkey`・`send` の MX と SPF・`_dmarc`）
- Resend のドメインの設定（追跡の設定など）と、既存の API キーには触れない
- Wing 専用のキーを別に作る（名前 `wing-production`、権限は送信だけ、送れるドメインは `sen-no-kaze.com`）。問題があれば、このキーだけを止める
- ドメインを別のチームへ移さない（移すと、元のチームはこのドメインで送れなくなる）

アプリの側でも、共有の上限に配慮して送ります（`lib/mail/send.ts`）。

| 仕組み | 内容 |
| --- | --- |
| 間をあけて送る | 1 通ごとに 250 ミリ秒あける。Resend の API の速さの上限は、チームのすべてのキーで共有のため |
| 速さの上限（429） | 指示された待ち時間が 2 秒以内なら 1 回だけ送り直す。それでも送れなければ、送信待ちのまま次の回へ回す |
| 送信数の上限（429。1 日・1 か月） | 失敗として残し、その回は止める（上限が戻った瞬間にまとめて送らない）。お知らせの画面に理由が出る |
| 二重送信の防止 | `Idempotency-Key` に通知の ID を使う（24 時間）。同時に 2 か所から送っても、送り直しても 1 通になる |
| 1 時間の上限 | 1 時間に送る通知は 30 件まで（`MAIL_MAX_PER_HOUR` で変えられる）。超えた分はメールを送らず、お知らせの画面にだけ残す（理由も出る）。お問い合わせは誰でも送れるため、いたずらの連続送信で共用の送信数を使い切らないように |
| 通信の失敗・Resend の障害（5xx） | 送信待ちのまま次の回へ回す |
| そのほかの失敗（キー・差出人の誤りなど） | 失敗として残す（お知らせの画面に理由が出る） |

送信数の上限は、プランごとにチーム全体で共有です。プランと今の送信数は、千の風様に Resend の画面（Usage）で確かめていただきます。

## 環境変数（Vercel の Production）

| 名前 | 内容 |
| --- | --- |
| `RESEND_API_KEY` | Wing 専用のキー。「Sensitive」で保存する（値が画面に出ない） |
| `MAIL_FROM` | 差出人。例：`千の風 <no-reply@sen-no-kaze.com>`（ドメイン認証済みのアドレス） |
| `MAIL_REPLY_TO` | 返信先。千の風様が毎日見ているアドレス。アドレスだけを書く（複数ならカンマ区切り）。形が正しくなければ付けずに送る |
| `MAIL_MAX_PER_HOUR` | 任意。1 時間に送る通知の上限（既定 30） |

`RESEND_API_KEY` と `MAIL_FROM` の両方があるときだけ送ります。入れた後に再デプロイが要ります。

## Supabase Auth（本番の画面で設定する）

| 項目 | 値 |
| --- | --- |
| SMTP | ホスト `smtp.resend.com`、ポート 465、ユーザー名 `resend`、パスワードは Resend のキー、差出人は `MAIL_FROM` と同じアドレスと名前 |
| メールの文面 | 会員登録の確認：`supabase/templates/confirmation.html`、パスワード再設定：`supabase/templates/recovery.html`。件名は `supabase/config.toml` の `[auth.email.template.*]` |
| Site URL・Redirect URLs | www（`docs/custom-domain-settings.md`） |
| 送信数の上限（Rate Limits） | 1 時間あたりのメールの数を、運用に足り、かつ Resend のプランの上限（1 日・1 か月）を使い切らない値にする。会員登録・再設定・確認メールの送り直しは誰でも申し込めるため、上限が大きすぎると、いたずらの申し込みで共用の送信数を使い切るおそれがある |
| Confirm email | 本部先行の運用開始の時に ON（2026-11-25 千の風様のご判断）。同じ時に `supabase/config.toml` の `enable_confirmations` も true にする |

`supabase config push` は本番では使いません。SMTP など本番の画面で入れた値を、設定ファイルの値で上書きするおそれがあるためです。文面は画面に貼り付けます。

## 本番の手順

1. 千の風様が当方を Resend のチームに招待する（役割は Member）。当方が Wing 専用のキーを作る
2. 作業の時間帯を、前もって千の風様に知らせる
3. 送られずに残っている通知（`email_status = 'pending'`）が 0 件かを、件数だけ確かめる（過去の通知を送らないため）
4. Vercel に環境変数を入れて、再デプロイする
5. Supabase の SMTP と文面を設定する
6. 下の表で送信を確かめる
7. 運用開始の時に Confirm email を ON にする

## 送信の確認

| 経路 | 確かめること |
| --- | --- |
| お問い合わせ | 本部に届く。返信すると返信先へ届く |
| 見積依頼 | 本部に届く。メールのリンクから案件を開ける |
| パスワード再設定 | 届く。www のまま最後まで再設定できる |
| 会員登録の確認 | 届く。同じブラウザで開くとログインした状態になる。別の端末で開くと、確認の後にログインの画面で案内が出る |
| 確認メールの送り直し | 登録の直後の画面と、確認がまだのアカウントのログインの画面から送れる |
| 届き方 | Gmail・携帯のメール・会社のメールで、迷惑メールに入らない |
| 過去の通知 | 送られていない |

試験の宛先は、当方のアドレスと試験用のアカウントだけにします。存在しないアドレスへ送ると、チーム全体の送信の評価が下がるためです。
