# Wingシステム｜業者さん向け正式実装・確認事項 2026-09-27

## 1. この文書の目的

2026-09-27 に実ブラウザで、シミュレーター → 保存 → 見積依頼 → 管理画面 → 現地条件 → 改訂見積 → 顧客承諾 → 契約確認 → 製造・施工 → 引渡し・アフター → 災害時提供までを確認した結果を、正式実装側へ引き継ぐ。

今回のUI整理PRでは、表示・操作性だけを修正する。
DB、RLS、SECURITY DEFINER RPC、Quote lifecycle、契約Revision、製造・引渡し状態などの正本は変更しない。

重要事項は以下から先に確認すること。

1. 本番migration backlogと実DB schema
2. Configuration保存の部分成功
3. 案件プランボード読取RPC
4. QuoteRequest / 概算見積 / 確定見積 / 承諾の状態遷移
5. 顧客が選んだ代理店組織へのroutingと代理店内主担当
6. 契約対象Revision固定

---

## 2. 実ブラウザで確認済みの重大事項

### A. Configuration保存が部分成功する

保存時に本番環境で以下のエラーを確認した。

```
Could not find the 'site_location_undecided' column of 'configurations' in the schema cache
```

一方、エラー後にも保存したプラン自体はマイページへ残った。

現行 `SupabaseStore.saveConfiguration` は、

1. `save_configuration` RPC
2. `configurations` への設置予定地UPDATE

を別処理で実行している。

そのため 1 が成功し 2 が失敗すると、利用者には失敗表示でもConfiguration本体が残る。

#### 必須確認

- 本番の LOCAL / REMOTE migration history
- `configurations.site_prefecture`
- `configurations.site_municipality`
- `configurations.site_location_undecided`
- PostgREST schema cache
- 現在のmigration backlogと適用順序

単一migrationだけを「とりあえず」適用しないこと。

#### 正式修正

保存操作を業務上1操作として扱い、途中失敗で部分保存を残さない。
既存の金額・権限境界を崩さず、transaction / RPCを含めて最小構成を設計する。

再試行時の重複Configurationも確認すること。

---

### B. 案件プランボードが本番で「読み込み不可」

管理画面の「プランボード」タブは、シミュレーターと同じ表示ロジックを再利用する実装が既にある。

しかし本番では、

```
この案件の保存済みプランボードを読み込めませんでした。
Configurationとの紐付けと閲覧権限を確認してください。
```

となった。

現行コードは `get_case_plan_configuration` RPCを使用し、RPC未適用時
（PGRST202 / 42883）は案件画面全体を落とさずプランボードだけ未表示にする。

リポジトリには以下が存在する。

```
supabase/migrations/20260922050000_case_plan_configuration_read.sql
```

#### 必須確認

- 本番に上記RPCが存在するか
- migration backlog上の前提・適用順
- Quote.configuration_id → Configuration の紐付け
- admin / master dealer / assigned dealer の閲覧権限
- RLSを広げずRPCで必要範囲だけ読む設計が維持されているか

正常化後は、保存したシミュレーター内容の平面図・外観・立面図・設備仕様を案件画面で確認できること。

---

### C. 第1版の概算見積を承諾でき、契約確認へ進める

実ブラウザで、第1版・概算見積の「この見積で進める」を押すと、

- Quote が「承諾」
- 管理画面の現在フェーズが「契約確認」
- 「次にやること：契約内容を確認」

へ進むことを確認した。

その時点で別途工事は未確定、現地確認完了の正式記録も無い。

#### 正式な期待フロー

```
見積依頼
→ 概算見積（現地確認前）
→ 代理店受付
→ 現地確認
→ 施工金額反映
→ 確定見積Revision発行
→ 顧客確認
→ 顧客承諾
→ 契約確認
```

#### 必須修正

UIだけでなく、server action / RPC / DB側でも
「契約工程へ進められる見積」の条件を保証する。

少なくとも「第1版だから不可」のような番号だけの判定ではなく、
将来のRevision運用を踏まえて「確定見積として承諾可能な状態」を正式に定義すること。

旧版（superseded）や非最新Revisionの承諾可否も確認する。

## 3. 代理店決定の正式フロー

現在の管理画面には本部管理者が担当代理店を割り当てる操作がある。

ただし正式な業務方針は以下。

```
顧客が代理店を検索・選択
→ 見積依頼を選択した代理店組織へrouting
→ 代理店管理者が組織内の主担当者を決定
→ 担当者がお客様へ連絡
```

本部による代理店割当は、例外・再割当・救済操作として残す方向。

### 実装時の注意

- 「代理店組織」と「担当者アカウント」を同一IDとして扱わない
- organizations / organization_memberships の現行設計を先に確認する
- 顧客が選んだorganizationをQuoteRequest / caseへどう固定するか決める
- 組織内担当者の割当と通知を分離する
- RLS / ACLは組織境界で確認する
- 本部の例外権限は監査可能にする

代理店検索・選択UI自体は現時点では保留。
正式routingのDB設計を先に確定しても、不要な公開UIを先行追加しない。

## 4. Quote lifecycle

現行では見積依頼送信時に、

- QuoteRequest
- 見積番号
- 第1版Quote
- quote_items snapshot

まで作成される。

そのため「見積依頼」と「正式見積」が業務上近すぎる。

既存仕様を全廃するのではなく、以下の意味を明確にする。

### 概算見積

- 現地確認前
- 工場生産分を中心とした概算
- 現地条件で変動する費用は未確定
- 顧客が確認できる
- 契約工程へ進める正式承諾の対象にはしない

### 確定見積

- 現地条件確認後
- 代理店が施工金額等を反映
- 新しいQuote Revisionとして発行
- 過去Revisionは履歴として保持
- 顧客が契約へ進む判断を行う対象

### 再見積

シミュレーターへ戻って仕様を編集する導線自体は既にある。

不足しているのは、発行済み見積に対して顧客が
「この部分を変更して再見積してほしい」と依頼し、
依頼理由・対応・新Revisionまで追跡する正式な状態／履歴。

必要な最小構成を設計し、既存Quote snapshotを上書きしない。

## 6. 契約

現在は顧客承諾後に「契約・図面・資料」の参考画面まで進む。

ただし、

- 正式契約状態
- 契約対象Quote Revision
- 契約書
- 署名
- 支払条件
- 入金状態

は未実装。

### 正式フロー

```
確定見積の顧客承諾
→ 契約対象Revision固定
→ 契約条件確認
→ 契約書作成・保存
→ 署名／書面契約記録
→ 契約成立
→ 着手条件確認
→ 製造依頼
```

Published / accepted Quoteを後から書き換えて契約内容を変えない。
内容変更時は新Revisionを作り、どのRevisionを契約したか固定する。

複数テーブル更新が1操作になる場合はtransactionで原子的に処理する。

- 製造対象Revision固定
- 製造指示
- 製造個体番号
- 棟数
- 製造開始日
- 製造完了日

発注済み・製造済み・施工済みとは扱わない。

- 引渡し確認

## 9. 災害時提供

現行画面は案件情報を参考表示しているだけで、
供給可否・供給可能棟数を判定していない。この挙動は維持する。

正式実装時の正本は案件や見積ではなく、引渡し後の完成個体／資産。

```
引渡し完了
→ 完成個体登録
→ 現在地・所有関係・移動可否
→ 災害時提供意思
→ 即時提供可否
→ 供給可能棟数集計
```

顧客の提供意思は同意・変更・撤回を履歴化する。

## 10. 「注文範囲」の扱い変更

以前は、

- 本体のみ
- 標準装備
- フル装備

等を先に選ぶ思想があった。

現在の正式方針は、

```
標準見積の内容をシミュレーターへ表示
→ 顧客が商品・仕様を変更
→ 実際の見積明細そのものを案件内容として扱う
```

とする。

したがって、UI上の「注文範囲」表示は廃止方向。

ただし内部の `finish_level` は、
カテゴリー範囲・価格計算・既存データ・RPC等へ依存しているため、
UI削除と内部カラム／ロジック削除を分離する。

### 禁止

- UIから消えたという理由だけで `finish_level` を即削除しない
- 既存Quote / Configurationの意味を変換せずにmigrationしない
- 本番データを一括更新しない

内部依存を調査し、不要化できる場合だけ別PRで整理する。

## 11. 案件管理の性能

実ブラウザで `/admin/quotes` の初回表示に数分かかるケースを確認した。

現行admin pathでは、案件一覧表示時に複数の全件系取得を並列で行い、
さらに選択案件の詳細ワークスペースも初期表示する。

### 調査

- DB query数
- 各query実行時間
- listAllQuotes
- listAllConfigurations
- listProfiles
- listContactMessages
- selected CaseWorkspaceの追加query
- 不要な全列取得
- 一覧に不要な詳細データ
- pagination / lazy detail loadingの必要性

タイムアウト時間を伸ばすだけの対応はしない。

Quote lifecycleや権限条件を変えず、一覧取得と詳細取得を分離できるか優先して確認する。

## 13. 検証・完了状態

この文書で「確認済み」は実ブラウザ／現行コードで確認したことを意味する。

以下を混同しない。

- コード実装
- CI成功
- PRマージ
- migration適用
- 実DB schema確認
- 本番DB検証
- 本番反映

本番migrationを扱うPRは、base SHA・HEAD・適用済みmigration・未適用migration・適用順を明示する。

権限、Quote lifecycle、契約Revision、transaction、Storage/RLSを含むPRは独立レビューを行う。
