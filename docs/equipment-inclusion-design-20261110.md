# 設備包含カテゴリー｜実装設計と停止条件（2026-11-10）

## 正本・目的

確定事項は「商品に含まれる設備をカテゴリー単位で登録」「通常はコンパクト表示」「シミュレーターでは『ユニットに含まれています』」「別室への追加設備は区別」「正式金額はDB保証」「既存Published Revision / Snapshotを変更しない」。

現行の `option_conflicts` は「商品ID対商品IDの同時選択禁止」であり、設備包含の正本にはしない。3点ユニットがトイレ・洗面を含むことと、別室の単体トイレを追加できることは両立させる。

## 現在地（2026-11-10読み取り確認。後日live再確認する）

- GitHub mainはPR #622を含み、PR #623も確認中にマージ。組合せ制限の登録とコンパクト表示は既存機能。
- 本番Supabaseの `options` / `option_categories` / `option_conflicts` は存在し、設備包含の専用テーブルは存在しない。
- `configuration_items` は `option_id` とnullableな `slot_code` を持つ。v2.5の位置枠は既に導入されているが、既存のトイレ・洗面の単体選択すべてに位置識別があるわけではない。
- `standard_estimate_revision_baseline_items` は `slot_code` を持つ。本番で確認した主要設備カテゴリーのbaseline slot登録件数は0件。

- 関連open PRには商品登録画面を変更する #563・#535、金額処理を変更する #618、商品データを変更する #616 などがある。PR差分、migration順序とbaseを毎回live確認する。

## PR分割

1. **PR1／このブランチ**：`lib/domain/equipment-inclusion.ts` の純粋な分類関数＋単体テスト＋本設計書。DB・画面・保存・金額は一切変えない。カテゴリーIDを使い、設置関係は呼出元が明示。位置関係不明では包含済みにしない。
2. **PR2／DB保存構造**：`option_included_categories (option_id, included_category_id)` を第一候補とする。両カラムにFK、組合せunique、自己カテゴリーの包含やdraft/retiredカテゴリー、商品削除時の挙動、書込み権限、監査、既存Published商品の編集可否を設計レビューする。不要なPUBLIC EXECUTEを与えない。migration新規作成と使い捨てDBの実行時検証が必要。本番適用は業者さん作業。
3. **PR3／商品登録**：STEP1の「この商品に含まれる設備」を折りたたみ、STEP2で差分を確認、保存は承認済みのDB経路のみ。#623の現行レイアウトを起点とし、#563・#535との重複変更を避ける。
4. **PR4／シミュレーター**：選択済み包含元と対象設備の位置関係を確定させ、「ユニットに含まれています」を表示。別室追加の入力を区別。位置が不明な時は勝手に重複選択を解除しない。
5. **PR5／正式金額・見積ガード**：DB/RPC側で同一設備の二重計上を防ぎ、保存・見積依頼・見積下書き・発行の各入口で整合検証。既存のPublished Revision・発行済みSnapshotは不変。PR #618との金額ロジック整合を検証する。

PR2・PR5は高リスクで独立レビュー必須。PR4も保存・Revisionに作用する部分は独立レビューを行う。いずれもマージ前に最新main/open PRと競合を再確認し、本番DBへは書き込まない。

## PR1の境界

`resolveEquipmentInclusion` は**表示用の分類のみ**。呼出元が選択済みの包含元と対象との位置関係を確定した場合だけ `included-in-unit` を返す。位置不明は `placement-undetermined` とする。

この結果を、正式な0円計上・選択削除・保存許可・見積発行判定に直接利用してはならない。将来のDB検証・金額ルールが合意・実装されるまで既存の処理を維持する。公開済みRevisionやSnapshotの金額はliveの商品包含設定を使って書き換えない。
