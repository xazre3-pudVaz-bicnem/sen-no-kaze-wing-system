# 設備包含カテゴリー｜DB・RPC設計審査メモ（2026-11-10）

この資料は**設計レビュー用**。ここに書いたSQL構造を本番へ適用したり、既存設定を削除する許可ではない。業務上未確定の扱いは明記し、決定済みとして実装しない。

## 1. GitHub / 本番Supabaseのread-only確認

- 主な関連テーブル：`options`、`option_categories`、`option_conflicts`、`configuration_items`、`standard_estimate_revision_baseline_items`、`quote_draft_items`、`quote_items`、`configuration_snapshots`。
- 本番に設備包含専用のテーブルはない。設備の重複を表す`option_conflicts`は2行あり、下記2件：
  - `3点ユニットバス 1216（浴槽・トイレ・洗面一体）` → `洗面器 KB-PR012-03-G141`（個別商品IDへの排他）。
  - `シャワートイレユニット 1116` → `トイレ（温水洗浄便座ウォッシュレット）`（個別商品IDへの排他）。
- `option_conflicts`が商品ID単位なのに対し、今回の包含はカテゴリーID単位。2件を新しいDB関係に**自動変換・削除しない**。新しい選択判定と正式金額のDBガードが成立し、別室追加の実装が完了した後の個別移行判定とする。
- `configuration_items.slot_code`は存在するが、v2.5の保存は公開済み標準見積Revisionの位置枠で検証する。任意の`slot_code`追加で別室に対応できるとは判断しない。
- 本番の`public.can_edit_catalog()`は現在`current_role_rank() >= 2`。未マージPR #502は本部管理者限定へ変更予定。権限を新規に重複実装せず、確定した本部編集権限を利用する設計とする。
- 既存の`SupabaseStore.setOptionRelations`はDELETE→INSERTの複数操作で**原子的ではない**。設備包含の設定をここに単純追加しない。
- 本番DBのmigrationは現時点で105件適用済み。最終`20261104100000_unused_draft_variant_safe_delete`。コードのmigration末尾と実DB適用状態を混同しない。
- 競合し得るopen PR：#502（商品編集権限）、#535/#563（商品編集UI）、#616（商品データ削除）、#618（金額計算）。PR作業時・マージ直前に再確認。

## 2. 保存テーブルの第一候補（既存マスターのIDだけを参照）

`public.option_included_categories`

| 列 | 用途 |
| --- | --- |
| `option_id uuid` | 包含元の商品。`options.id`参照 |
| `included_category_id uuid` | 含まれる設備。`option_categories.id`参照 |
| `created_at timestamptz` | 登録日時（履歴そのものは専用監査ログ） |

- 主キー`(option_id, included_category_id)`。登録順は業務上不要。金額・quantity・部屋ID・独立Revision IDは増やさない。
- 対象の行削除で無条件に関係を失わないよう、FKの削除時動作を事前レビューする。推奨は初期段階`RESTRICT`。商品削除RPCへの影響を検証する。
- 新テーブルは初期状態で空。既存の`options`、`option_conflicts`、標準見積／発行済みデータへマイグレーションで書き込まない。

## 3. 保存APIの安全条件

**推奨：単一RPCで包含関係の差し替え。** `set_option_included_categories(option_id, expected_category_ids, next_category_ids)` に相当する公開境界を設ける。

1. `auth.uid()`を確認し、商品台帳の実際の編集権限をDB側で確認。権限未確定／権限なしなら拒否。
2. 引数UUIDの重複・存在・カテゴリーの有効性を検査（受理するカテゴリーの範囲は別途合意）。
3. 対象の`options`行を`FOR UPDATE`でロック。同じ商品の同時編集を直列化し、現在の関係集合を`expected_category_ids`と比較。不一致は競合として全体を拒否する。
4. 同じトランザクション内で関係を差し替える。変更前後のカテゴリーID集合・実行者を監査ログへ記録。途中失敗時は全操作ロールバック。
5. `SECURITY DEFINER`が必要なら`search_path`固定、すべてschema-qualified、owner／EXECUTE／RLS bypass／helper公開範囲を明示。PUBLIC/anonのEXECUTEを許さず、許可ロールにも必ず業務権限を再確認。
6. テーブル直接更新は原則許さず、一覧閲覧のみ最小のSELECTを付与。APIへの露出・RLS・GRANTは独立して検証。
7. 下書き・公開済み商品の参照や、商品データ自体の変更との原子性を再確認。既存の`saveOptionAction`の後に別RPCを追加するだけでは、商品本体と包含設定の一括原子性は保証されない。必要なら包含専用のSTEP1→STEP2確認→正式保存とする。

## 4. シミュレーター／正式金額の不変条件

- **新規選択で同一設置先の重複設備を禁止**し、単体設備の明細と包含された設備を同時に正式計上しない。
- 別室への設備追加は、本体ユニット内の包含とは別の設置単位で識別し、独立した有償明細として扱う。現状の`slot_code`だけで表せるかは未確定。
- 新しい正本はDB/RPC側。UIで0円表示にするだけ、既存商品の価格を0にするだけ、標準明細を隠すだけでは完了ではない。
- 標準見積Revision・見積Draft・見積発行・構成保存のそれぞれで、現行の計算と検証の入口を監査する。個別の商品IDの排他が残って別室選択を妨げる状態は完了としない。
- 既存Published Revision・Snapshotは書き換えない。過去の見積・発行済みSnapshotを**最新の包含マスターで再計算して別金額にしない**。新たな保存／新たなRevisionに対する価格ルールと、その時点の包含状態の固定方法は設計審査対象。

## 6. マージ・本番適用の停止条件

- **新規migrationファイルはローカルSupabase CLIで生成**し、すべて新規ファイルとして追加する。既存適用済みmigrationは編集しない。
- リポジトリのテスト（型チェック／lint／単体）と、使い捨てDBでのmigration適用・RLS／EXECUTE／同時編集・失敗ロールバック検証が完了するまでDB PRをマージしない。
- 高リスクDB／金額／Revision変更は、実装者と異なる独立レビューを通す。レビュー結果は「マージ可／修正後マージ可／マージ不可」で明記する。
- 本番migration適用・本番商品データ変更・既存排他2件の移行は、**事前承認まで禁止**。mainへのマージだけで本番利用可能とは扱わない。
